# مواصفة تنفيذ API والمزامنة Offline-First

**الحالة:** عقد التنفيذ الحالي؛ توجد الآن واجهة أولية للموافقة واستقبال العمليات وموجز الأحداث، بينما تخزين الهاتف والمزامنة على الجهاز لم ينفذا بعد.
**التاريخ:** 2026-11-02

## 1. حدود التنفيذ

- PostgreSQL هو المصدر المعتمد للحالة المشتركة بعد قبول العملية من الخادم.
- SQLite محلي على الجهاز هو مخزن العمل المحلي والـ outbox، وليس مصدرًا معتمدًا للطرف الآخر.
- لا تُرسل أي عملية مالية قبل حفظها محليًا مع envelope ثابت داخل معاملة SQLite واحدة.
- لا تُنشأ دفعة إلكترونية ولا يُنفذ تحويل مالي. سجل payment يعني واقعة دفع يقرّ بها الأطراف، لا حركة مصرفية.
- لا يعتمد العميل على ساعة الهاتف لترتيب الأحداث أو حسم التعارضات.

## 2. عقد HTTP API المقترح

كل المسارات تتطلب هوية مصادقًا عليها من طبقة Auth موثوقة. actor_user_id لا يؤخذ من body أو query؛ يستخرج من الجلسة/الرمز بعد التحقق. كل طلب يمر بفحص عضوية العلاقة وصلاحية العملية على الخادم.

| Method | Path | الوظيفة |
|---|---|---|
| POST | /v1/relationships/{relationshipId}/operations | استقبال أمر جديد بمفتاح idempotency |
| GET | /v1/relationships/{relationshipId}/operations?after={sequence} | مزامنة الأحداث الجديدة بترتيب الخادم |
| POST | /v1/relationships/{relationshipId}/operations/{operationId}/decision | موافقة/رفض مع expectedVersion |
| POST | /v1/relationships/{relationshipId}/obligations | إنشاء التزام بعد تحقق حالة الموافقة |
| POST | /v1/relationships/{relationshipId}/payments | تسجيل دفعة وفق سياسة العلاقة |
| POST | /v1/relationships/{relationshipId}/allocations | تخصيص مبلغ من دفعة إلى التزام محدد |
| GET | /v1/relationships/{relationshipId}/balances | الرصيد المفتوح لكل عملة على حدة |
| GET | /v1/relationships/{relationshipId}/account-cycles | الدورة الحالية والدورات المؤرشفة وأرصدة كل دورة |
| GET | /v1/relationships/{relationshipId}/statement | كشف حساب قابل للاستكمال |

### ضوابط كل طلب

- Idempotency-Key UUID ثابت لكل أمر محلي؛ لا يتغير عند timeout أو retry.
- expectedVersion إلزامي عند اتخاذ قرار أو تعديل aggregate.
- كل قيمة مالية integer minor units موجبة، مع currency صريحة من YER/SAR/USD.
- لا يقبل الخادم actor_user_id من العميل.
- يربط الخادم العملية بالعلاقة والمستخدم والجهاز ويعيد canonical IDs وserverVersion وserverSequence.
- التخصيص لا يتم افتراضيًا FIFO؛ يجب تحديد obligation ID والمبلغ صراحة.
- لا يقبل الخادم تخصيصًا يتجاوز غير المخصص من الدفعة أو المتبقي من الالتزام.
- إعادة استخدام مفتاح idempotency مع payload مختلف يجب أن تُرفض.

### أشكال النتائج القياسية

- accepted: قبل الخادم العملية وأعاد هويتها وتسلسلها.
- already_processed: أعاد نتيجة العملية الأصلية لنفس المفتاح والـ request hash.
- needs_approval: حُفظ المقترح بانتظار موافقة مخولة.
- conflict_stale_version: النسخة قديمة؛ لا يعاد تطبيق الأمر.
- forbidden: لا توجد عضوية/صلاحية كافية.
- validation_error: مبلغ أو عملة أو مرجع غير صالح.
- temporarily_unavailable: يعاد الطلب نفسه بالمفتاح نفسه.

## 3. مخطط SQLite المحلي

الجداول المحلية الأساسية المقترحة:

- local_operations(operation_id PRIMARY KEY, relationship_id, operation_type, schema_version, payload_json, request_hash, base_server_version, local_state, created_at_device, attempts, last_error)
- outbox(operation_id PRIMARY KEY REFERENCES local_operations, queued_at, next_attempt_at)
- local_events(server_sequence PRIMARY KEY, relationship_id, event_json, received_at)
- sync_cursors(relationship_id PRIMARY KEY, last_server_sequence)
- local_attachments(id PRIMARY KEY, relationship_id, local_uri, checksum, upload_state)

قواعد التخزين:
1. إنشاء السجل المحلي وoutbox في transaction واحدة.
2. operation_id ثابت لا يتغير عند إعادة المحاولة.
3. لا يُحذف السجل المحلي عند timeout؛ النتيجة غير معروفة حتى رد الخادم.
4. synced يعني قبول الخادم، وليس بالضرورة موافقة الطرف الآخر.
5. حالات الأعمال (pending/approved/rejected/disputed) منفصلة عن حالات النقل (queued/sending/synced/conflict/failed).
6. كل cursor مستقل لكل علاقة، ولا تُخلط أحداث العلاقات.
7. قاعدة البيانات المحلية مشفرة، ومفتاحها محفوظ في مخزن مفاتيح النظام، وليس داخل ملفات التطبيق.

## 4. دورة المزامنة

1. تحميل outbox حسب dependency order.
2. إرسال operation envelope كما حُفظ محليًا دون إعادة توليد IDs.
3. الخادم يصادق المستخدم والجهاز ثم يفحص idempotency والعضوية والصلاحيات.
4. تنفيذ العملية والنتيجة وسجل التدقيق وتحديث version/sequence في معاملة PostgreSQL واحدة.
5. إعادة نتيجة canonical.
6. العميل يحفظ الرد محليًا ويحدّث حالة النقل.
7. سحب أحداث الخادم بعد last_server_sequence وتطبيقها بترتيب sequence داخل معاملة SQLite.
8. عند conflict، حفظ العملية المتعارضة وإظهار الحالة الحالية؛ لا Last-Write-Wins ولا حذف للمحاولة.

## 5. اختبار هاتفين دون إنترنت ثم المزامنة

يُنفذ على جهازين فعليين أو محاكيين مستقلين مع قاعدة SQLite منفصلة لكل جهاز:

1. إنشاء حسابين وعلاقة مشتركة بعد الاتصال.
2. تنزيل حالة العلاقة على الجهازين ثم قطع الإنترنت عنهما.
3. الجهاز A يسجل التزامًا محليًا؛ إغلاق التطبيق وإعادة فتحه والتأكد من بقائه.
4. الجهاز B لا يرى الالتزام قبل المزامنة.
5. إعادة الاتصال على A؛ إرسال نفس operation ID مرتين عمدًا مع محاكاة timeout بعد قبول الخادم.
6. التأكد من وجود عملية واحدة فقط ونتيجة idempotent واحدة.
7. B يسحب الحدث ويراه awaiting_counterparty لا approved.
8. B يوافق بإصدار version الحالي؛ A يسحب قرار الموافقة ويراه بترتيب الخادم.
9. تسجيل دفعة وتخصيصها جزئيًا؛ التحقق من المتبقي في الدفعة والالتزام على الجهازين.
10. إنشاء قرارين متعارضين على نسختين قديمتين؛ يجب قبول قرار واحد فقط وإرجاع conflict للآخر.
11. إيقاف التطبيق قسرًا أثناء وجود outbox ثم إعادة تشغيله؛ لا فقد ولا تكرار.
12. التحقق من تطابق ledger وbalance حسب العلاقة والعملة بعد اكتمال المزامنة.

لا يُعلن نجاح اختبار الهاتفين قبل إرفاق إصدار التطبيق، نوع الجهاز/المحاكي، سجل الخطوات، وعدد العمليات، ونتيجة reconciliation.

## 6. خطة قياس الأداء قبل ادعاء قابلية التوسع

### أحجام البيانات التجريبية
مجموعات اصطناعية متدرجة: 10 آلاف، 100 ألف، مليون، ثم 10 ملايين عملية مالية. هذه أحجام اختبار مقترحة وليست توقعات فعلية لعدد المستخدمين.

### القياسات
- p50/p95/p99 لقراءة كشف الحساب والرصيد وإنشاء عملية ومزامنة cursor.
- throughput للقراءة والكتابة.
- زمن معالجة دفعات sync المتراكمة بعد عودة الاتصال.
- lock waits/deadlocks، CPU، RAM، I/O، حجم الفهارس، وحجم WAL.
- أداء علاقة ضخمة مقارنة بعدد كبير من العلاقات الصغيرة.
- إعادة الاختبارات مع 1 و10 و50 و100 عميل متزامن بعد تثبيت بيئة الاختبار.

### شروط صدق النتائج
- توثيق CPU/RAM/Storage وإعداد PostgreSQL وإصدار الأدوات.
- نشر seed generator وrandom seed وSQL scripts.
- تكرار كل قياس عدة مرات، وعدم اختيار أفضل محاولة فقط.
- لا تُحدد أهداف latency/throughput نهائية قبل معرفة الأجهزة والاتصال وحجم الاستخدام الفعلي.
- مليون مستخدم مسجل ليس مليون مستخدم متزامنًا؛ يلزم DAU، العمليات لكل مستخدم، ذروة الكتابة، sync burst، ومعدل المرفقات قبل حساب السعة.

## 7. ما نُفذ وما لم يُنفذ بعد

- نُفذت واجهة HTTP أولية لقرارات الموافقة/الرفض، واستقبال operation envelope، وقراءة الأحداث بمؤشر cursor داخل العلاقة.
- أضيفت دورة تصفير ثنائية: `POST /v1/relationships/:relationshipId/settlement-reset-requests` لإنشاء الطلب، و`GET /v1/relationships/:relationshipId/settlement-reset-requests/pending` لعرض الطلب للطرف الآخر، و`POST /v1/relationships/:relationshipId/settlement-reset-requests/:requestId/decision` للموافقة أو الرفض. لا يستطيع مقدم الطلب اتخاذ القرار، ويشترط طرفان نشطان وصلاحية موافقة للطرف المقابل.
- تتحقق الواجهة من هوية principal المحققة عبر resolver محقون؛ لا يوجد حتى الآن مزود مصادقة أو token verifier أو تسجيل OTP.
- يُحسب request hash على الخادم، ويمنع تكرار operation ID بمحتوى مختلف.
- لكل علاقة server sequence مستقل؛ إنشاء العملية وتغيير حالتها ينتجان أحداثًا غير قابلة للتعديل.
- الموافقة على credit_charge/payment/allocation تُنشئ السجل المالي وترحيله إلى دفتر القيود ضمن معاملة واحدة.
- أُضيفت حزمة Flutter للـ outbox المحلي ومطبق الأحداث وSyncCoordinator وHTTP transport، مع مسار فتح SQLCipher ومفتاح في secure storage.
- اختبارات منطق التخزين تستخدم SQLite FFI غير مشفر؛ لا تثبت بعد عمل SQLCipher native أو Android Keystore على جهاز فعلي.
- يوجد اختبار محاكاة لعميلين مستقلين بقاعدتي SQLite منفصلتين، يشمل timeout بعد قبول الخادم وإعادة الإرسال بنفس operation ID ثم التقارب عبر الأحداث.
- لم يُنفذ بعد اختبار هاتفين فعليين أو دورة end-to-end متصلة بقاعدة PostgreSQL الحقيقية.
- يوجد قياس اصطناعي لمليون عملية ومليون حدث، وقياس دورة مالية عند 1/10/50 عاملاً؛ النتائج موثقة في `docs/POSTGRES_SCALE_BENCHMARK_2026-11-02.md`. هذه نتائج CI اتجاهية وليست ضمان سعة إنتاجية أو مليون مستخدم متزامن.
- لا توجد بعد آلية استعادة/نسخ احتياطي لمفتاح SQLCipher أو اختبار استرجاع قاعدة محلية.
- طلب التصفية والقرار النهائي ينتجان أحداثًا داخل موجز العلاقة نفسه؛ operationId يكون null لأحداث التصفية. أثناء انتظار القرار تُمنع العمليات الجديدة. الموافقة تعيد فحص الرصيد ثم تؤرشف دورة الحساب الحالية وتنشئ دورة جديدة بعنوان «صفحة بيضاء» مع بقاء العلاقة التجارية نشطة؛ الرفض يسجل كحدث غير قابل للتعديل ويبقي الدورة الحالية كما هي ويعيد قبول العمليات. مزود المصادقة الحقيقي واختبار العميلين على أجهزة فعلية ما زالا غير منفذين.

## 9. دورة تصفير الحساب الثنائية — migrations 007–008

### المسارات
- POST /v1/relationships/{relationshipId}/settlement-reset-requests
- GET /v1/relationships/{relationshipId}/settlement-reset-requests/pending
- POST /v1/relationships/{relationshipId}/settlement-reset-requests/{requestId}/decision
- GET /v1/relationships/{relationshipId}/account-cycles

### قواعد التنفيذ
1. v1 يتطلب طرفين نشطين بالضبط في العلاقة.
2. مقدم الطلب لا يستطيع اتخاذ القرار على طلبه؛ القرار من الطرف المقابل النشط ذي صلاحية can_approve.
3. طلب واحد فقط يمكن أن يبقى قيد الانتظار في العلاقة.
4. تجمّد العمليات الجديدة في العلاقة طوال انتظار القرار، باستخدام قفل صف العلاقة المشترك بين قبول العمليات وإنشاء/اعتماد طلب التصفير.
5. الموافقة تعيد فحص الالتزامات غير المسددة والدفعات غير المخصصة والعمليات المعلقة/المتنازع عليها داخل معاملة القرار نفسها؛ ثم تؤرشف دورة الحساب الحالية وتنشئ دورة جديدة. العلاقة التجارية تبقى active، ولا تتغير العضوية أو الأدوار أو الصلاحيات.
6. الرفض يبقي الدورة الحالية والعلاقة كما هما، ويسمح باستئناف العمليات.
7. الطلبات والقرارات غير قابلة للتعديل أو الحذف، وإعادة الطلب/القرار بنفس idempotency key تعيد النتيجة الأصلية.
8. أحداث الطلب والموافقة والرفض تضاف إلى relationship_events لتصل للطرفين عبر cursor sync؛ أحداث التصفير تحمل operationId: null.

### قراءة الدورات والأرصدة
GET /v1/relationships/{relationshipId}/account-cycles يعيد الدورة الحالية والدورات المؤرشفة، مع أرصدة كل دورة حسب مالك الحساب والعملة. لا تظهر بيانات العلاقة إلا لعضو نشط فيها؛ المستخدم غير العضو يحصل على 403، والعلاقة غير الموجودة على 404.

- currentCycleId: معرّف الدورة الحالية.
- cycles[]: رقم الدورة وعنوانها وحالتها وتواريخ بدايتها/نهايتها وbalances[].
- balances[]: ownerUserId وcurrency، إضافة إلى أربعة أرصدة مستقلة:
  - receivableMinor: ذمم هذا العضو المدينة لصالحه، وتساوي SUM(debit-credit) لحساب party_receivable.
  - payableMinor: الذمم المستحقة على هذا العضو، وتساوي SUM(credit-debit) لحساب party_payable.
  - unappliedPaymentAssetMinor: دفعات سجلها العضو ولم يخصصها، وتساوي SUM(debit-credit) لحساب unapplied_payment_asset.
  - unappliedPaymentLiabilityMinor: دفعات استلمها العضو ولم تخصص، وتساوي SUM(credit-debit) لحساب unapplied_payment_liability.
- balanceSemantics = separate_account_classes_minor_units. لا تجمع الفئات الأربع في صافي واحد ولا تخصم الدفعة غير المخصصة من الذمم؛ تسجيل الدفعة وحده لا يسدد التزامًا. كل قيمة ترسل كنص عشري لحماية دقة bigint/numeric. العملة مستقلة ولا يوجد جمع بين YER/SAR/USD.
- الدورة الجديدة الخالية من القيود تعيد balances: []، أي لا توجد حركات مالية مسجلة فيها حتى الآن.
- الوصول مقصور على العضو النشط في العلاقة، مع 401 لغير المصادق و403 لغير العضو و404 لعلاقة غير موجودة.

طبقة المصادقة ما زالت تعتمد على PrincipalResolver المحقون ولا تمثل تسجيل دخول إنتاجيًا.

### تصفير الحساب والصفحة البيضاء — تحديث migration 008

- العلاقة لا تُغلق عند اعتماد التصفير. يظل `relationships.status = active`.
- `account_cycles` يحتفظ بالدورة الحالية والدورات المؤرشفة لكل علاقة.
- العمليات والقيود المالية مرتبطة بـ `cycle_id`، ويُضاف `cycleId` إلى أحداث المزامنة.
- بعد موافقة الطرف المقابل، تُؤرشف الدورة القديمة ويُنشأ رقم دورة جديد برصيد افتتاحي صفر. جميع السجلات التاريخية تبقى محفوظة.
- يمنع الخادم تخصيص دفعة أو التزام بين دورتين مختلفتين.
- الرفض لا ينشئ دورة جديدة ولا يغير الدورة الحالية.


## تحديث 2026-11-02 — عملية المرتجع
- نوع العملية الجديد `sales_return` يمر عبر inbox المعتاد ويظل `awaiting_counterparty` حتى موافقة الطرف الآخر.
- payload: `originalObligationId`, `currency`, `amountMinor`, و`reason` الاختياري. هوية البائع والمشتري تؤخذ من الالتزام الأصلي ولا يثق النظام بأطراف يرسلها العميل.
- بعد الاعتماد تُنشأ `ledger.sales_returns` ويُرحّل قيد عكسي إلى `journal_entries` داخل معاملة الاعتماد نفسها. تجاوز مجموع المرتجعات لقيمة الالتزام يرفض ويعيد معاملة الاعتماد كاملة.
- أرصدة `receivableMinor` و`payableMinor` أصبحت قيمًا موقعة: السالب يعني رصيدًا دائنًا/حقًا للطرف المقابل، والموجب يعني رصيدًا مستحقًا وفق اتجاه فئة الحساب. لا تقص القيم عند الصفر.
- لم تتم إضافة HTTP route مخصص أو واجهة مستخدم لطلب المرتجع في هذا التغيير؛ طبقة قبول العمليات الحالية تحتاج ربط العميل بهذا النوع. ولا يوجد تنفيذ لرد نقدي فعلي حتى الآن.

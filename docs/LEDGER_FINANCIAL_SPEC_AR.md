# المواصفة المالية للدفتر — Shared Commercial Ledger

**الحالة:** مواصفة تنفيذية مرجعية للنسخة الحالية، تفصل المنفذ عن المتبقي.  
**المراجعة:** 2026-11-02 | **المخطط:** ledger، migrations 001–008.  
**ERD:** [DATABASE_ERD_AR.md](./DATABASE_ERD_AR.md)

> الدفتر يسجل الالتزامات والدفعات المبلغ عنها والتخصيصات والقيود. لا يحرك أموالًا ولا يمثل بنكًا أو بوابة دفع.

## 1. مبادئ ملزمة

1. لكل عملية مالية علاقة واحدة وعملة واحدة ودورة حساب واحدة.
2. العملات الحالية YER وSAR وUSD؛ لا جمع أو تحويل أو مقاصة ضمنية بينها.
3. المبالغ تخزن كـ bigint في وحدات العملة الصغرى، ولا تستخدم floating point.
4. كل قيد متوازن: مجموع المدين يساوي مجموع الدائن داخل المعاملة والعملة نفسيهما.
5. القيود والحقائق المالية المنشورة لا تعدل ولا تحذف؛ التصحيح يكون بقيد تعويضي جديد. سير عمل العكس الكامل لم يكتمل بعد.
6. حالة العمل منفصلة عن حالة المزامنة؛ العملية المحلية غير المتزامنة ليست تأكيدًا مشتركًا.
7. لا تخصيص FIFO تلقائي؛ يلزم تخصيص صريح.
8. لا مدفوعات إلكترونية أو أسعار صرف تلقائية في النطاق الحالي.

## 2. مفردات الدفتر

| المفهوم | المعنى | أثره |
|---|---|---|
| operation | أمر أعمال داخل العلاقة | لا يثبت أثرًا ماليًا بمفرده |
| obligation | مبلغ مستحق من مدين إلى دائن | يزيد المستحق |
| payment | مبلغ مسجل من دافع إلى مستفيد | يسجل أولًا غير مخصص |
| allocation | ربط مبلغ من دفعة بالتزام | يخفض الذمم ويستهلك غير المخصص |
| journal transaction | رأس قيد مالي | مصدر احتساب الرصيد |
| account cycle | صفحة حالية أو مؤرشفة | تحدد نطاق كشف الحساب |

توريد البضاعة من النوع supply لا ينشئ مديونية وحده في التنفيذ الحالي. إنشاء الالتزام يتم عبر credit_charge معتمد.

## 3. العملية والاعتماد

- تسجل العملية في ledger.operations بمعرف operation_id وبصمة الطلب والعلاقة وصاحب العملية والنوع والحالة وإصدار الخادم.
- ledger.accept_operation تتحقق من قبول العملية والعضوية والصلاحيات وتضيف الحدث المتسلسل.
- قرار العملية يسجل في ledger.approvals. يجب أن يكون صاحب القرار عضوًا نشطًا لديه can_approve، وألا يكون منشئ العملية، وأن يطابق expected_server_version الإصدار الحالي.
- القرار idempotent؛ إعادة الطلب نفسه تعيد النتيجة، وإعادة استخدام المفتاح بمحتوى مختلف ترفض.
- لا تعتمد حالة العملية من العميل مباشرة.

## 4. القيود المالية الفعلية

### 4.1 الالتزام المعتمد — credit_charge

يجب أن يكون مصدر obligation عملية معتمدة من النوع credit_charge، وأن يكون منشئ العملية هو الدائن. trigger ينشئ:

| الحساب | مدين | دائن |
|---|---:|---:|
| party_receivable — ذمم الدائن | مبلغ الالتزام | — |
| party_payable — ذمم المدين | — | مبلغ الالتزام |

### 4.2 الدفعة — payment

يجب أن يكون مصدر payment عملية معتمدة من النوع payment، ومنشئها أحد طرفي الدفعة. تسجل أولًا غير مخصصة:

| الحساب | مدين | دائن |
|---|---:|---:|
| unapplied_payment_asset — أصل غير مخصص لدى الدافع | مبلغ الدفعة | — |
| unapplied_payment_liability — التزام غير مخصص لدى المستفيد | — | مبلغ الدفعة |

لا تخفض الدفعة فاتورة بعينها قبل تخصيصها.

### 4.3 تخصيص الدفعة — allocation

يشترط:
- الدفعة confirmed والالتزام open.
- الدافع هو المدين والمستفيد هو الدائن.
- العملة والعلاقة متطابقتان.
- مصدر التخصيص عملية معتمدة من النوع allocation.
- المبلغ موجب، ولا يتجاوز مجموع التخصيصات قيمة الدفعة أو الالتزام.
- الدفعة والالتزام وعملية التخصيص في دورة الحساب نفسها.

القيد الناتج يعيد تصنيف أربعة أرصدة:

| الحساب | مدين | دائن |
|---|---:|---:|
| التزام الدفعة غير المخصصة لدى المستفيد | مبلغ التخصيص | — |
| ذمم المستفيد المدينة | — | مبلغ التخصيص |
| ذمم الدافع الدائنة | مبلغ التخصيص | — |
| أصل الدفعة غير المخصصة لدى الدافع | — | مبلغ التخصيص |

هذا لا ينشئ نقدًا جديدًا ولا يكرر تسجيل الدفعة.

## 5. ثوابت PostgreSQL

- العملة مقيدة إلى YER/SAR/USD، والمبالغ موجبة.
- كل سطر قيد إما مدين موجب أو دائن موجب، وليس كليهما.
- رأس القيد ومصدره وحساباته ضمن العلاقة والعملة نفسيهما.
- فحص توازن القيد مؤجل إلى نهاية المعاملة.
- القيود والالتزامات والمدفوعات والتخصيصات والموافقات والأحداث وقرارات التصفير محمية من التعديل/الحذف وفق triggers الموجودة.
- تخصيصات الدفعات مقفلة أثناء فحص المجاميع لمنع تجاوز الحدود بالتزامن.
- كل عملية جديدة تلتحق بالدورة الحالية، ويمنع تخصيص عبر الدورات.
- يوجد حد فريد لدورة نشطة واحدة لكل علاقة.

## 6. احتساب الرصيد وعقد API

مصدر الحقيقة أسطر `journal_entries` المرتبطة بـ`journal_transactions.cycle_id` والحسابات المملوكة لكل طرف. لا تجمع فئات الحسابات الأربع في رقم صافٍ واحد؛ لأن ذلك قد يخفي التزامًا قائمًا مقابل دفعة غير مخصصة. مثال: إذا كان على المشتري 5,000 YER وسجل دفعة 5,000 YER لم تخصص بعد، فالمشتري يملك أصل دفعة غير مخصص 5,000 وفي الوقت نفسه عليه ذمم 5,000؛ لا يجوز إظهار صافي صفر وكأن الدين سُدد.

يعيد المسار:
`GET /v1/relationships/{relationshipId}/account-cycles`
أرصدة منفصلة لكل مالك حساب وعملة ودورة:

| الحقل | طريقة الحساب | المعنى |
|---|---|---|
| `receivableMinor` | ذمم الدائن: SUM(debit-credit) | مستحق لهذا العضو من الطرف المقابل |
| `payableMinor` | ذمم المدين: SUM(credit-debit) | مستحق على هذا العضو للطرف المقابل |
| `unappliedPaymentAssetMinor` | أصل الدفعة لدى الدافع: SUM(debit-credit) | دفعات سجلها العضو ولم يخصصها بعد |
| `unappliedPaymentLiabilityMinor` | التزام الدفعة لدى المستفيد: SUM(credit-debit) | دفعات استلمها العضو ولم تخصص بعد |

كل القيم أعداد صحيحة بوحدة العملة الصغرى، وتُرسل كنص عشري لحماية bigint/numeric من فقد الدقة في JavaScript. القيم الأربع غير سالبة في مسارات الترحيل الحالية. تعرض YER/SAR/USD منفصلة. لا يُستخدم `net_position_minor` وحده كحقل «له/عليه»، ولا تُقاص الدفعة غير المخصصة مع الذمم. لا تعرض الواجهة «صافي المستحق» من هذه الحقول إلا وفق قواعد تخصيص معتمدة؛ الرصيد المستحق هو الذمم المفتوحة، والدفعة غير المخصصة تظل بندًا مستقلاً حتى تخصيصها.

اختبار PostgreSQL للمسار المالي يثبت قبل التخصيص: ذمم الدائن 5,000 والتزام الدفعة غير المخصصة للمستفيد 5,000، وذمم المدين 5,000 وأصل الدفعة غير المخصصة للدافع 5,000. وبعد التخصيص الكامل تصبح فئات الحساب الأربع صفرًا.

## 7. التصفير والصفحة البيضاء

التصفير لا يغلق العلاقة التجارية. يشترط عدم وجود التزامات غير مسددة أو دفعات غير مخصصة أو عمليات معلقة/متنازع عليها في الدورة الحالية. الطلب المعلق يوقف العمليات الجديدة.

- مقدم الطلب لا يعتمد طلبه بنفسه.
- الطرف المقابل النشط المخول يتخذ القرار.
- الرفض يبقي الدورة الحالية ويرفع التجميد.
- الموافقة تعيد التحقق تحت القفل، تؤرشف الدورة الحالية وتنشئ دورة جديدة برصيد افتتاحي صفر، مع بقاء العلاقة والأعضاء والصلاحيات.
- التاريخ القديم لا يحذف، وتحتوي أحداث المزامنة على cycleId.

## 8. فجوات التنفيذ الحالية

1. لا توجد جداول مستخدمين/هويات أو أجهزة أو جلسات أو OTP ضمن schema ledger.
2. لا توجد جداول مرفقات أو ملفات إثبات.
3. لا توجد جداول مستقلة للمرتجعات/الإشعارات الدائنة أو طلبات العكس والتعديلات الكاملة.
4. مبدأ append-only موجود، لكن سير عمل العكس بقيد تعويضي وربط إلزامي وموافقة مناسب غير مكتمل.
5. توجد API لاستعراض ملخص الدورات وأرصدة فئات الحساب الأربع؛ API كشف تفصيلي للعمليات والقيود المرفقة بالدورة لم يكتمل بعد.
6. لا توجد سياسة إقفال فترات أو ترحيل رصيد افتتاحي غير صفري؛ الصفحة البيضاء تبدأ بصفر.
7. لا توجد تحويلات عملات أو مقاصة متعددة العملات.
8. لا توجد مصادقة إنتاجية أو RLS مثبتة؛ يجب فرض عزل العلاقة في API لكل قراءة وكتابة.
9. لا يجوز استخدام obligations.status أو payments.status وحدهما لحساب الرصيد؛ المرجع هو دفتر القيود والتخصيصات، وأي void/close يجب أن يثبت أثره الدفتري.

## 9. مصفوفة الاختبارات

| السيناريو | المطلوب | الحالة المعروفة |
|---|---|---|
| قيد الالتزام | توازن مدين/دائن بالقيمة نفسها | مغطى باختبارات PostgreSQL |
| قيد الدفعة غير المخصصة | لا يخفض التزامًا محددًا | مغطى |
| تخصيص جزئي/متعدد | لا يتجاوز المتبقي | مغطى |
| اختلاف العملة/العلاقة | رفض التخصيص المخالف | مغطى بقيود واختبارات |
| إعادة المحاولة | لا يتكرر القيد | مغطى باختبارات idempotency |
| الصفحة البيضاء | أرشفة الدورة وبقاء العلاقة | Run #94 ناجح |
| دورة مالية كاملة: دين + دفعة + تخصيص + تصفير | إثبات صفر قبل التصفير وحفظ الأرشيف وصفر الجديدة | اختبار E2E مستقل مطلوب |
| العكس/المرتجعات | قيد تعويضي لا يمحو الأصل | غير مكتمل |
| تفسير إشارة الرصيد | له/عليه صحيح لكل طرف | عقد API واختبارات عرض مطلوبة |

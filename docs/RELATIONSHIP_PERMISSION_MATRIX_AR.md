# نموذج الصلاحيات ومصفوفة الوصول — الإصدار الأول

**التاريخ:** 2026-11-02  
**الحالة:** خط أساس تصميمي للحزمة 0؛ لا يدّعي اكتمال مصادقة الإنتاج أو واجهات إدارة الموظفين.  
**المرجع:** `PRD_2.0_AR.md`

## 1. مبادئ التفويض

1. الهوية تثبت من هو المستخدم؛ العضوية تحدد العلاقات التي ينتمي إليها؛ الصلاحية تحدد ما يستطيع فعله داخل علاقة محددة.
2. لا توجد صلاحية عالمية باسم «تاجر» أو «عميل». الدور التجاري وصف سياقي وليس تفويضًا تلقائيًا.
3. كل تحقق صلاحية يتم على الخادم لكل طلب، وليس في الواجهة فقط.
4. افتراضيًا Deny: أي عملية غير منصوص عليها ممنوعة.
5. لا يستطيع منشئ العملية اعتمادها عندما تتطلب موافقة الطرف المقابل.
6. مدير النظام لا يكتسب صلاحية مالية لمجرد كونه مدير النظام.
7. إلغاء العضوية يمنع الوصول الجديد ولا يحذف السجل التاريخي أو يغير القيود.
8. أي تصحيح مالي يتم بقيد تعويضي وتدقيق، لا بتعديل أو حذف.

## 2. الكيانات والصلاحيات

- **Authenticated user:** هوية موثقة.
- **Device:** جهاز مسجل مرتبط بالمستخدم، قابل للإلغاء.
- **Relationship member:** عضوية نشطة في علاقة بعينها.
- **Relationship role label:** وصف مثل merchant/customer/supplier/buyer؛ لا يمنح صلاحية وحده.
- **Permission set:** أذونات صريحة مرتبطة بالعضوية وسياسة العلاقة.
- **Approval policy version:** نسخة السياسة النافذة للعملية عند إنشائها.
- **System operator:** دعم وتشغيل النظام؛ لا يملك صلاحية تعديل الدفتر.

## 3. مصفوفة صلاحيات العضوية الثنائية

الرموز: **نعم** = مسموح عند استيفاء شروط العملية؛ **مشروط** = يتطلب إذنًا صريحًا أو تحققًا إضافيًا؛ **لا** = ممنوع.

| قراءة العلاقة وكشفها | نعم | نعم | لا | لا افتراضيًا |
| إنشاء مقترح عملية | نعم، ضمن أنواع دوره | نعم، ضمن أنواع دوره | لا | لا |
| تعديل مسودة محلية غير مرسلة | نعم، منشئها فقط | نعم، منشئها فقط | لا | لا |
| إرسال العملية للخادم | نعم | نعم | لا | لا |
| اعتماد/رفض العملية | لا على عمليته | نعم، إذا كان الطرف المقابل ومخولًا | لا | لا |

## 4. الصلاحيات المنطقية

تستخدم أسماء مستقرة لا ترتبط بالواجهة:
- `relationship.read`
- `operation.create`
- `operation.submit`
- `operation.approve`
- `operation.reject`
- `dispute.create`
- `dispute.resolve`
- `payment.create`
- `allocation.create`
- `settlement.request`
- `settlement.decide`
- `correction.request`
- `correction.approve`
- `attachment.read`
- `relationship.policy.manage`
- `device.revoke`

لا تُمنح أي صلاحية عبر اسم الدور فقط. يجب ربطها بعضوية نشطة وبالعلاقة المستهدفة وبنوع العملية ومالك السجل والسياسة النافذة.

## 5. قواعد حاسمة

- الطرف الذي أنشأ العملية لا يعتمدها إذا كان القرار يتطلب الطرف الآخر.
- `can_approve` في schema الحالي هو مؤشر اعتماد محدود، وليس بديلًا عن التحقق من أن المعتمد هو الطرف المقابل أو عن تحقق نوع العملية.
- يجب رفض أي قرار على نسخة قديمة من العملية بتعارض واضح؛ لا استبدال القرار السابق.
- قرار الموافقة/الرفض idempotent: إعادة المفتاح ونفس المحتوى تعيد النتيجة نفسها؛ إعادة المفتاح بمحتوى مختلف ترفض.
- العضو غير النشط لا يقرأ ولا يكتب ولا يزامن عمليات جديدة.
- كل استثناء دعم/تشغيل يسجل actor, target, reason, timestamp, before/after، ولا يسمح بتغيير journal entries.

## 6. حدود الإصدار الأول وما لم ينفذ

- النموذج المالي الأول ثنائي الطرفين.
- أضيفت identity schema في migration 010 ومسارات OTP/جلسات/أجهزة/ملف شخصي؛ لا يوجد مزود SMS فعلي أو تركيب تشغيل إنتاجي موحد، لذلك لا تعتبر المصادقة جاهزة للإطلاق.
- `relationship_members` تحتوي role_label وstatus وcan_approve؛ `can_approve` ليس RBAC دقيقًا لكل فعل. migration 011 تضيف طلبات الربط وقبولها/رفضها، ولا تزال صلاحيات الموظفين/المتاجر خارج v1.
- لا توجد إدارة موظفين أو صلاحيات على مستوى المتجر في الإصدار الأول.
- إنشاء العلاقة الثنائية والدعوة والقبول/الرفض وعزل العضوية الأولي مدمج في PR #35 ومختبر في PostgreSQL Run #161 وApproval API Run #86. لا تعتبر بقية الصلاحيات في المصفوفة منفذة لمجرد توثيقها؛ ما لم يثبت باختبار يبقى Pending.

## 7. اختبارات إلزامية للصلاحيات

- عضو غير موجود أو غير نشط لا يستطيع القراءة أو الكتابة أو المزامنة.
- عضو في علاقة A لا يستطيع استخدام معرف علاقة B للوصول إلى عملية أو مرفق.
- منشئ العملية لا يستطيع اعتمادها نيابة عن الطرف المقابل.
- عضو نشط بلا `operation.approve` لا يعتمد ولا يرفض.
- عضو مخول لكنه ليس الطرف المقابل لا يعتمد.
- مدير النظام لا يعدل أو يحذف journal entry ولا يوافق على عملية بدل طرف.
- تغيير السياسة لا يغير أثر العمليات المنشأة وفق نسخة السياسة السابقة.
- إلغاء جهاز يمنع أي sync لاحق بهويته الملغاة.

# نموذج الصلاحيات ومصفوفة الوصول — الإصدار الأول

**التاريخ:** 2026-11-02  
**الحالة:** خط أساس تصميمي للحزمة 0؛ لا يدّعي اكتمال مصادقة الإنتاج أو واجهات إدارة الموظفين.  
**المرجع:** `PRD_2.0_AR.md`

## 1. مبادئ التفويض

1. الهوية تثبت من هو المستخدم؛ العضوية تحدد العلاقات التي ينتمي إليها؛ الصلاحية تحدد ما يستطيع فعله داخل علاقة محددة.
2. لا توجد صلاحية عالمية باسم «تاجر» أو «عميل». الدور التجاري وصف سياقي وليس تفويضًا تلقائيًا.
3. كل تحقق صلاحية يتم على الخادم لكل طلب، وليس في الواجهة فقط.
4. افتراضيًا Deny: أي عملية غير منصوص عليها ممنوعة.
5. لا يستطيع منشئ العملية اعتمادها عندما تتطلب موافقة الطرف المقابل.
6. مدير النظام لا يكتسب صلاحية مالية لمجرد كونه مدير النظام.
7. إلغاء العضوية يمنع الوصول الجديد ولا يحذف السجل التاريخي أو يغير القيود.
8. أي تصحيح مالي يتم بقيد تعويضي وتدقيق، لا بتعديل أو حذف.

## 2. الكيانات والصلاحيات

- **Authenticated user:** هوية موثقة.
- **Device:** جهاز مسجل مرتبط بالمستخدم، قابل للإلغاء.
- **Relationship member:** عضوية نشطة في علاقة بعينها.
- **Relationship role label:** وصف مثل merchant/customer/supplier/buyer؛ لا يمنح صلاحية وحده.
- **Permission set:** أذونات صريحة مرتبطة بالعضوية وسياسة العلاقة.
- **Approval policy version:** نسخة السياسة النافذة للعملية عند إنشائها.
- **System operator:** دعم وتشغيل النظام؛ لا يملك صلاحية تعديل الدفتر.

## 3. مصفوفة صلاحيات العضوية الثنائية

الرموز: **نعم** = مسموح عند استيفاء شروط العملية؛ **مشروط** = يتطلب إذنًا صريحًا أو تحققًا إضافيًا؛ **لا** = ممنوع.

|---|---:|---:|---:|---:|
| قراءة العلاقة وكشفها | نعم | نعم | لا | لا افتراضيًا |

| تعديل مسودة محلية غير مرسلة | نعم، منشئها فقط | نعم، منشئها فقط | لا | لا |
| إرسال العملية للخادم | نعم | نعم | لا | لا |
| اعتماد/رفض العملية | لا على عمليته | نعم، إذا كان الطرف المقابل ومخولًا | لا | لا |
| فتح اعتراض/طلب توضيح | نعم | نعم | لا | لا |
| اتخاذ قرار على الاعتراض | لا على اعتراضه إذا كان القرار للطرف الآخر | نعم حسب السياسة | لا | لا |
| تسجيل دفعة | نعم | نعم | لا | لا |

| اعتماد تصفير الدورة | لا لطلبه | نعم، الطرف المقابل النشط | لا | لا |
| طلب عكس/تعديل | نعم مع سبب ومرجع أصل | نعم مع سبب ومرجع أصل | لا | لا |

| قراءة المرفقات | نعم إذا كانت مرتبطة بعلاقته ومصرحًا بها | نعم إذا كانت مرتبطة بعلاقته ومصرحًا بها | لا | لا افتراضيًا |
| إدارة عضوية الطرف الآخر | لا | لا | لا | دعم محدود بلا تغيير مالي |
| تغيير إعدادات الموافقة | مشروط بصلاحية relationship_policy_admin | مشروط بصلاحية relationship_policy_admin | لا | لا |
| إلغاء جهازه | نعم، بعد تحقق الهوية | نعم، بعد تحقق الهوية | لا | دعم أمني موثق فقط |

## 4. الصلاحيات المنطقية

تستخدم أسماء مستقرة لا ترتبط بالواجهة:
- `relationship.read`
- `operation.create`
- `operation.submit`
- `operation.approve`
- `operation.reject`
- `dispute.create`
- `dispute.resolve`
- `payment.create`
- `allocation.create`
- `settlement.request`
- `settlement.decide`
- `correction.request`
- `correction.approve`
- `attachment.read`
- `relationship.policy.manage`
- `device.revoke`

لا تُمنح أي صلاحية عبر اسم الدور فقط. يجب ربطها بعضوية نشطة وبالعلاقة المستهدفة وبنوع العملية ومالك السجل والسياسة النافذة.

## 5. قواعد حاسمة

- الطرف الذي أنشأ العملية لا يعتمدها إذا كان القرار يتطلب الطرف الآخر.
- `can_approve` في schema الحالي هو مؤشر اعتماد محدود، وليس بديلًا عن التحقق من أن المعتمد هو الطرف المقابل أو عن تحقق نوع العملية.
- يجب رفض أي قرار على نسخة قديمة من العملية بتعارض واضح؛ لا استبدال القرار السابق.
- قرار الموافقة/الرفض idempotent: إعادة المفتاح ونفس المحتوى تعيد النتيجة نفسها؛ إعادة المفتاح بمحتوى مختلف ترفض.
- العضو غير النشط لا يقرأ ولا يكتب ولا يزامن عمليات جديدة.
- كل استثناء دعم/تشغيل يسجل actor, target, reason, timestamp, before/after، ولا يسمح بتغيير journal entries.

## 6. حدود الإصدار الأول وما لم ينفذ

- النموذج المالي الأول ثنائي الطرفين.
- أضيفت identity schema في migration 010 ومسارات OTP/جلسات/أجهزة/ملف شخصي؛ لا يوجد مزود SMS فعلي أو تركيب تشغيل إنتاجي موحد، لذلك لا تعتبر المصادقة جاهزة للإطلاق.
- `relationship_members` تحتوي role_label وstatus وcan_approve؛ `can_approve` ليس RBAC دقيقًا لكل فعل. migration 011 تضيف طلبات الربط وقبولها/رفضها، ولا تزال صلاحيات الموظفين/المتاجر خارج v1.
- لا توجد إدارة موظفين أو صلاحيات على مستوى المتجر في الإصدار الأول.
- إنشاء العلاقة الثنائية والدعوة والقبول/الرفض وعزل العضوية الأولي مدمج في PR #35 ومختبر في PostgreSQL Run #161 وApproval API Run #86. لا تعتبر بقية الصلاحيات في المصفوفة منفذة لمجرد توثيقها؛ ما لم يثبت باختبار يبقى Pending.

## 7. اختبارات إلزامية للصلاحيات

- عضو غير موجود أو غير نشط لا يستطيع القراءة أو الكتابة أو المزامنة.
- عضو في علاقة A لا يستطيع استخدام معرف علاقة B للوصول إلى عملية أو مرفق.
- منشئ العملية لا يستطيع اعتمادها نيابة عن الطرف المقابل.
- عضو نشط بلا `operation.approve` لا يعتمد ولا يرفض.
- عضو مخول لكنه ليس الطرف المقابل لا يعتمد.
- مدير النظام لا يعدل أو يحذف journal entry ولا يوافق على عملية بدل طرف.
- تغيير السياسة لا يغير أثر العمليات المنشأة وفق نسخة السياسة السابقة.
- إلغاء جهاز يمنع أي sync لاحق بهويته الملغاة.

## 8. نموذج الأدوار المطلوب مقابل المنفذ فعليًا

| الدور المطلوب | التمثيل الحالي | حالة v1 | ملاحظة |
|---|---|---|---|
| المالك (Owner) | `relationships.created_by_user_id` والمُنشئ الأول للعلاقة | غير منفذ كدور | لا توجد صلاحيات مالك صريحة ولا تفويض موظفين |
| مسؤول المبيعات | لا يوجد | غير منفذ | يحتاج تصميم موظفين/متجر قبل أي migration |
| المسؤول المالي | لا يوجد | غير منفذ | يحتاج تصميم موظفين/متجر قبل أي migration |
| الطرف المقابل (عميل/مورد) | عضوية نشطة في `relationship_members` بدور `customer/supplier` | منفذ جزئيًا | يقرر في العمليات التي تخصه، ولا يعتمد عملياته هو |
| أدمن النظام | لا يوجد كيان تشغيلي | غير منفذ | لا يملك أي مسار مالي؛ triggers قاعدة البيانات تمنع تعديل الدفتر |

**قاعدة عدم الخلط:** صلاحيات المالك/المبيعات/المالية تخص التاجر وحده. الطرف المقابل ليس موظفًا لدى التاجر، ولا تُمنح صلاحياته عبر دور تجاري أو `role_label`؛ بل عبر عضويته النشطة في العلاقة وقراره في العمليات الموجهة إليه.

**حدود حالية:** `relationship_members` تحمل `role_label`, `status`, `can_approve` فقط. لا يوجد جدول صلاحيات دقيقة ولا كيان موظف/متجر. لذلك أي بند في هذه المصفوفة يخص الموظفين هو تصميم مطلوب، وليس تنفيذًا قائمًا.

## 10. فصل الإنشاء عن الاعتماد

- المنفذ حاليًا: `decide_operation` يرفض اعتماد المنشئ لعمليته (`op.actor_user_id = p_actor_user_id`).
- المنفذ حاليًا: قرار التصفير يرفض أن يقرر مقدم الطلب طلبه.
- غير منفذ: عندما ينشئ **موظف** عملية باسم التاجر، ما هو "المنشئ" الذي يُقارن؟ `actor_user_id` أم المالك الفعلي؟ هذا قرار مفتوح.
- غير منفذ: هل يمكن لموظف مبيعات إنشاء عملية ثم يعتمدها المسؤول المالي في نفس الجهة؟ يجب ألا يُسمح باعتماد داخلي يحل محل قرار الطرف المقابل.
- قرار مفتوح: العمليات الحساسة (`credit_charge`, `payment`, `sales_return`, التصفير، التصحيح) تتطلب دائمًا اعتماد الطرف المقابل، ويُفصل إنشاء الموظف عن اعتماد المالك/المالية إن سمح النموذج لاحقًا.

## 11. الفجوات مرتبة بالأولوية

| الأولوية | الفجوة | الأثر | ما يلزم |
|---|---|---|---|
| عالية | `supply` غير مسموح في HTTP رغم دعمه في DB | لا يمكن إرسال توريد من العميل عبر API | إصلاح enum/validation واختبار HTTP |
| عالية | لا فصل صلاحيات فعلي؛ `can_approve` فقط | أي عضو نشط مخول يعتمد أي نوع عملية | تصميم جدول صلاحيات بعد حسم نموذج الموظفين |
| متوسطة | لا تحقق صريح من أن المعتمد هو الطرف المقابل | يعتمد على شرط "ليس المنشئ" ووجود عضوين فقط | إضافة تحقق صريح أو إثبات invariants |
| متوسطة | لا إدارة موظفين/متجر | لا يمكن تطبيق أدوار المالك/المبيعات/المالية | تصميم كيان staff + grants قبل migration |
| متوسطة | لا حد ائتماني | لا يمكن تطبيق السيناريو المطلوب | قرار منتج ثم نموذج بيانات |
| منخفضة | لا تعديل/اعتراض عام | المرتجع يغطي تصحيحًا محددًا فقط | تصميم dispute/modification workflow |
| منخفضة | التقارير محدودة | لا تصدير/تقارير شاملة | تحديد تقارير v1 قبل التنفيذ |
| منخفضة | لا سياسة موافقة قابلة للتغيير | `can_approve` ثابت | ربط `approval_policy_version` بالعمليات |

## 13. قرارات مفتوحة لا تُثبّتها migration الآن

1. نموذج الموظفين: هل الموظف عضو في المتجر أم في العلاقة؟ وما علاقة دوره بصلاحيات العلاقة؟
2. هل يمكن للموظف إنشاء عملية باسم التاجر؟ ومن يُعد "المنشئ" لفصل الإنشاء عن الاعتماد؟
3. الحد الائتماني: تنبيه أم منع، ومن يملك تعديله؟
4. سياسة الموافقة: ثابتة لكل علاقة أم قابلة للنسخ والتغيير؟
5. هل يُبنى التصحيح العام على المرتجع أم نوع عملية مستقل؟
6. هل يُسمح بتفويض الاعتماد لموظف مالي، أم يبقى للطرف المقابل/المالك فقط؟

**لا تُنفذ migration 014 لهذه البنود قبل حسم 1–6.** المصفوفة الحالية توثيقية وتكشف الفجوات، ولا تدّعي أن RBAC الدقيق منفذ.
